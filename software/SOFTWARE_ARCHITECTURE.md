# 软件框架与系统分层设计

- 项目：ESP8266 两轮桌面机器人
- 状态：架构概念设计，待硬件接口和模块型号确认
- 版本：0.1

## 1. 软件目标
- 将 GPIO/I²C/PWM 等底层操作与运动控制、行为决策和显示分离。
- 统一管理待机、手动、自动模式与故障停止状态。
- 避免传感器读取、OLED 刷新或日志输出长期阻塞电机控制。
- 规范传感器数据、控制命令、状态信息和故障原因的数据流。
- 每个硬件模块可独立测试，方便逐步联调。

## 2. 推荐技术基线

| 项目 | 初步建议 | 说明 |
|---|---|---|
| 主控 | ESP8266 | 以实际开发板型号为准 |
| 语言 | C++ | 适合常见嵌入式生态 |
| 开发环境 | PlatformIO | 依赖与构建配置管理方便 |
| 框架 | Arduino Core for ESP8266 | 第一版优先简单易调试；若选 FreeRTOS 等方案需更新 |

| 配置 | 集中式配置头文件 | GPIO、阈值与功能开关统一管理 |

以上为建议，不表示固件已经实现。

## 3. 系统分层

L5 应用与行为层：RobotApp、状态机、手动控制、循迹和避障。
L4 服务层：MotionService、SensorService、UiService、Diagnostics，以及硬件支持后的 PowerMonitor。
L3 设备驱动层：MotorDriver、Dht11Driver、Mpu6050Driver、OledDriver、IrSensorDriver。
L2 HAL 与硬件适配层：GPIO、PWM、I²C、UART、时间和调度封装。
L1 平台层：Arduino Core、ESP8266 SDK 和芯片硬件。

### L1：平台与芯片层
提供 ESP8266 SDK、Arduino Core、GPIO、PWM、I²C、UART、Wi-Fi 等底层能力。应用层不应散布平台 API 调用。

### L2：HAL 与硬件适配层
封装 GPIO、PWM、I²C、UART、系统时间和周期调度，便于适配开发板差异。

### L3：设备驱动层
- MotorDriver：方向、PWM、使能和紧急停止。
- Dht11Driver：温湿度采样与有效性检查。
- Mpu6050Driver：I²C 初始化、原始数据读取和基本校验。
- OledDriver：清屏、绘图、表情与状态显示。
- IrSensorDriver：数字/模拟输入读取与基础滤波。

驱动层只提供设备能力，不决定机器人进入何种行为模式。

### L4：服务层
- MotionService：把目标方向/速度转换为左右轮命令，处理限幅与停止。
- SensorService：按周期采样，输出带时间戳和有效性标志的数据。
- UiService：将运行状态、表情、温湿度和错误信息转换为 OLED 页面。
- Diagnostics：统一日志、启动自检和故障计数。
- PowerMonitor：只有增加电压采样硬件后才能启用，不能假定当前硬件可直接测量电池电压。

### L5：应用与行为层
RobotApp 管理主循环和状态机；行为模块根据传感器输入生成运动目标；状态机统一仲裁模式切换、急停和故障状态。

## 5. 主要模块职责

| 模块 | 输入 | 输出/职责 |
|---|---|---|
| RobotApp | 系统事件、传感器快照、用户命令 | 调度模块并推动状态机 |
| RobotStateMachine | 当前状态、命令、故障标志 | 新状态与允许执行的行为 |
| MotorDriver | 左右轮方向与 PWM 请求 | 控制驱动器并提供 stop |
| MotionService | 目标方向、目标速度 | 左右轮控制值与限幅 |
| SensorService | 驱动读数 | 统一快照、时间戳和有效标志 |
| Dht11Driver | 采样请求 | 温度、湿度或读取错误 |
| Mpu6050Driver | I²C 读写 | 加速度/角速度原始值或换算值 |
| IrSensorDriver | GPIO/ADC 输入 | 红外检测结果或循迹状态 |
| UiService | 状态、传感器快照、错误 | OLED 表情、状态页和简要读数 |
| Diagnostics | 各模块事件 | 串口日志与故障统计 |

ESP8266 的 GPIO/ADC 资源有限；多个模拟红外输出不能默认全部直接连接，需按具体开发板核对。

## 6. 状态机概念设计

BOOT_SELFTEST：初始化串口、驱动、传感器和 OLED，输出启动结果。
IDLE：电机输出为零，显示待机表情与状态。
MANUAL：执行有效控制命令；命令超时或失联时停止电机。
AUTONOMY：按已启用的行为模块循迹或避障；第一版建议只实现一个明确的自动模式。
FAULT_STOP：立即停止电机，显示错误状态并记录日志；满足安全恢复条件后才返回待机。

状态转换建议：启动自检通过后进入 IDLE；收到有效手动命令进入 MANUAL；选择自动模式进入 AUTONOMY；停止命令返回 IDLE；严重故障从任意运行状态进入 FAULT_STOP。故障清除后重新自检，不直接恢复运动。

如果未来增加 Wi-Fi 遥控，网络命令应校验并经过超时和状态机仲裁，不要在网络回调中长时间执行电机控制。

## 7. 主循环与非阻塞调度

第一版可使用基于 millis() 的周期调度，不必一开始引入复杂 RTOS。以下为初始目标，需按实测调整。

| 任务 | 初始目标周期 | 说明 |
|---|---:|---|
| 电机命令更新 | 10–20 ms | 优先级高，避免阻塞 I²C 和长日志 |
| 红外采样 | 5–20 ms | 按模块响应速度调整 |
| MPU6050 采样 | 10–20 ms | 按运动检测需求调整 |
| DHT11 采样 | 1–2 s | 不适合高频重复采样 |
| OLED 刷新 | 100–250 ms | 内容变化或到期时刷新 |
| 串口诊断 | 事件触发/低频 | 限制日志量 |

原则：
- 常规运行路径避免长时间 delay。
- 每个周期任务独立计时，单次执行尽可能短。
- I²C 失败、传感器超时和无效数据应有明确处理路径。
- 数据携带时间戳与有效标志，行为层不能把旧数据当作新数据。
- 电机控制必须有停止命令和失联/超时停止策略。

## 8. 传感器与 OLED 数据流

DHT11、MPU6050 和红外传感器 → SensorService → 状态机/行为模块 → MotionService → MotorDriver。
SensorService 同时向 UiService 提供快照；UiService 调用 OledDriver 更新 0.96 英寸 OLED。

OLED 与 MPU6050 若都采用 I²C，可在地址、逻辑电压、上拉电阻和总线电容兼容时共用总线。常见 OLED 地址为 0x3C，MPU6050 常见地址为 0x68 或 0x69，但需以实物扫描与配置为准。

OLED 页面建议：启动状态、待机表情、运行模式、简要传感器信息（可选）、故障提示。0.96 英寸屏幕空间有限，不建议同时显示大量数值。

## 9. GPIO 分配策略

确认开发板型号前，不固定最终 GPIO 号码。将映射集中放入 board_config.h，并遵守：
- 避开 ESP8266 Flash 专用 GPIO（常见 GPIO6–GPIO11）。
- 注意 GPIO0、GPIO2、GPIO15 等启动绑带脚的上电电平要求。
- 根据开发板核对可用 PWM、I²C、UART 和 ADC 引脚。
- ESP8266 通常只有一个外部 ADC 输入通道，多个模拟红外输出不能默认都直接连接。
- OLED 与 MPU6050 共用 I²C 时，统一初始化 SDA/SCL。

## 10. 故障处理

| 故障 | 建议行为 |
|---|---|
| 传感器初始化失败 | 记录故障；禁用依赖该传感器的自动模式 |
| 红外读数无效/超时 | 停止或进入安全行为，不使用陈旧数据 |
| OLED 初始化失败 | 记录日志；显示降级不应阻止电机安全控制 |
| 控制命令失联/超时 | 左右轮输出归零 |
| I²C 总线错误 | 限次重试并记录，避免无限阻塞 |
| 严重故障 | 进入 FAULT_STOP，立即停止电机 |
| ESP8266 复位 | 启动时先保证驱动器处于停止/禁用状态 |

硬件上应尽量保证 ESP8266 复位、引脚浮空或未初始化时，电机驱动器默认不动作。

## 11. 测试策略
1. 构建空工程，确认 PlatformIO、板型和依赖版本。
2. 接主控前测量 5V/3.3V、极性和启动压降。
3. OLED 单独显示启动页面、表情和状态。
4. 扫描 I²C 总线，确认 OLED/MPU6050 地址与上拉电压。
5. 测试 DHT11 低频读取、超时和无效数据处理。
6. 测试红外安装方向、有效距离、输出电平和响应。
7. 抬起车轮，低 PWM 测左右电机方向和停止。
8. 验证待机、手动、自动、故障停止与恢复。
9. 整机测试电机启动时 ESP8266 是否复位、I²C 是否出错。
10. 每次修改供电、引脚或调度周期后执行回归测试。
